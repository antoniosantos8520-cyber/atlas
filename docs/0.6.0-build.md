# 0.6.0 build plan

Two features, asked for 2026-09-23: **a re-targetable node control window**, and **a movement
restrictor that refuses a move between rooms the map does not connect**.

**How this list is used.** One checkpoint at a time. Each one is built, then tested live in Foundry,
and only then ticked. A checkpoint that fails does not get ticked and does not get built past. Tick
the box yourself; do not let me tick it for you.

Nothing here is released. 0.5.0 is committed and unreleased too, so both ship together whenever a
release is cut.

---

## The decisions that govern this build

Settled 2026-09-23, in answer to a direct question. These are not open for re-litigation mid-build;
if one turns out wrong in play, it gets changed here first and the affected checkpoints reopen.

| | Decision | What it rules out |
|---|---|---|
| 1 | **One hop, endpoints only.** A move is legal when the room it starts in and the room it ends in are the same room, or are directly connected. | A to C is refused even when the drag physically sweeps across B. Reaching C means two moves. |
| 2 | **The Keeper is exempt, silently.** | No warning, no override key. The rule is for players. |
| 3 | **The panel holds line of sight, effects, and rename.** | No Delete and no connection matrix in the panel, deliberately: a dashboard is coming, and Delete one click from a node swap is a misfire waiting to happen. |
| 4 | **The panel body is a pure builder from the start.** | The dashboard mounts the builder later, so it must never depend on being inside a window. |

### Two facts this build rests on, both verified in the Foundry v14 client source

- **`preMoveToken` can refuse cleanly.** Returning `false` deletes the movement fields before any
  write and calls `#stopMovement`, so the token never leaves the room it is in. There is nothing to
  undo, and the teleport-back fallback is not needed.
- **Endpoints-only is not a compromise, it is the only thing that works everywhere.** On a gridded
  scene Foundry hands the hook every intermediate cell, so a path walk would be possible. On a
  gridless scene it hands over the endpoints and nothing else. ATLAS is built for hand-traced photo
  maps, which are usually gridless, so a path walk would silently behave differently from map to
  map.

### The trap this build must not fall into

A movement gate inside ATLAS would also apply to **a host system's own travel map**, which is an
ATLAS-shaped graph on a Foundry scene whose party marker moves by `token.update`. That fires
`preMoveToken`. Gating it would reverse two standing rulings about how travel works. So the gate
carries a `CONFIG` predicate that a host system widens, because ATLAS can only recognise its own
room labels and knows nothing about another system's markers, lamps or thrown weapons.

## Part A: the movement restrictor

- [ ] **A1. The pure decision, with tests.**
  One transform, no Foundry anywhere near it: given the area data and two room labels, is this step
  legal? Tests pin your own example, the A-B-C-D line: A to B legal, A to C refused, A to D refused,
  D to C legal, same room legal, either end in no room legal, and B to A treated as the same edge as
  A to B.
  *Test: `npm test` is green. Nothing to see in Foundry yet.*

- [ ] **A2. The gate, behind a world setting, off by default.**
  The hook, the setting, and the `CONFIG` skip predicate. Off by default because this is a published
  module and an upgrade must not change how anyone's game already moves.
  *Test: trace four rooms in a line, connect A-B, B-C, C-D. Turn the setting on. As a player, drag
  A to B and it goes. Drag A to C and the token does not move, with a message naming both rooms.*

- [ ] **A3. Everything that must NOT be gated.**
  The Keeper, room labels themselves, undo, paste, and a scene with no areas traced.
  *Test: as Keeper drag a creature A to C and it goes, silently. Drag a room label and it moves.
  Lock, Redraw and Clear all still work. On a scene with no areas, everything moves freely.*

- [ ] **A4. The host system registers its skip.**
  The host side, in the system, not in the module: party marker, ward lamps, thrown weapons.
  *Test: on the travel map, a Keeper drag of the party marker to a league that is not adjacent still
  works and still spends nothing. Ward lamps and thrown weapons drop and drag normally.*

- [ ] **A5. A refused move leaves the fog correct.**
  The boundary sensor has no preview guard, so a refused drag can leave the per-client record naming
  a room the token never entered.
  *Test: as a player, drag A to C, get refused, then move A to B legally. The fog is right at every
  step, and nothing is revealed that should not be.*

## Part B: the node control window

- [ ] **B1. One builder, two surfaces.**
  Lift the card body out of the marker sheet into a pure function, and have the existing sheet call
  it. No behaviour change at all in this checkpoint. Tests pin the produced HTML.
  *Test: double-click a room label. The card looks and behaves exactly as it does today, including
  the amber staged state and Apply being disabled until something changes.*

- [ ] **B2. The window, and the macro that opens it.**
  A single window, `ATLAS.openRoomPanel()`, so your macro is one line.
  *Test: run the macro. A window opens showing one room's controls, and toggling line of sight in it
  changes the map.*

- [ ] **B3. Left-click a node and the window follows.**
  The retarget, pinned per token instance rather than on the prototype, which is how the module
  already keeps host right-click menus off room labels.
  *Test: with the window open, left-click room A then room B then room C. One window throughout, and
  it always shows the room you last clicked. Token selection and dragging still work normally.*

- [ ] **B4. Rename in the panel.**
  *Test: rename a room in the panel. The map label changes and the editor's matrix agrees. Clear the
  name and it falls back to a letter.*

- [ ] **B5. Decide the double-click card's fate.**
  Two surfaces editing one room is how they drift, and the card does not repaint when the data
  changes underneath it. Options are to keep it as a fallback or to let the panel replace it. Not a
  decision to make before B3 is in your hands.
  *Test: whichever way it goes, double-clicking a label does one predictable thing.*

## Not in this build, but waiting

These are known and deliberately not scheduled. They are here so they are not rediscovered as
surprises.

- **The hex draw tool.** Spec'd 2026-09-05 and never built: draw one hex, and every later press
  stamps a copy of it. The seams are already scouted.
- **Orphaned rooms.** Delete a room's label token with the Delete key and its record, polygon and
  connections survive. The sweep that would fix this is written and tested but called from nowhere.
  The movement gate makes this worse, because it would enforce a room nobody can see or select.
- **Release chores.** `package.json` says 0.4.0 against `module.json`'s 0.5.0, the download URL
  still names the v0.4.0 zip, and the README claims v0.4.0 and 51 tests when 80 pass. These belong
  with a release being cut, not with a feature.
