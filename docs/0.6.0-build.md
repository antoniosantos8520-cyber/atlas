# 0.6.0 build plan

Two features, asked for 2026-09-23: **a re-targetable node control window**, and **a movement
restrictor that refuses a move between rooms the map does not connect**.

**How this list is used.** One checkpoint at a time. Each one is built, then tested live in Foundry,
and only then ticked. A checkpoint that fails does not get ticked and does not get built past. Tick
the box yourself; do not let me tick it for you.

Nothing here is released. 0.5.0 is committed and unreleased too, so both ship together whenever a
release is cut.

---

## The decisions that govern this build

Settled 2026-09-23, in answer to a direct question. These are not open for re-litigation mid-build;
if one turns out wrong in play, it gets changed here first and the affected checkpoints reopen.

| | Decision | What it rules out |
|---|---|---|
| 1 | **One hop, endpoints only.** A move is legal when the room it starts in and the room it ends in are the same room, or are directly connected. | A to C is refused even when the drag physically sweeps across B. Reaching C means two moves. |
| 2 | **The Keeper is exempt, silently.** | No warning, no override key. The rule is for players. |
| 3 | **The panel holds line of sight, effects, and rename.** | No Delete and no connection matrix in the panel, deliberately: a dashboard is coming, and Delete one click from a node swap is a misfire waiting to happen. |
| 4 | **The panel body is a pure builder from the start.** | The dashboard mounts the builder later, so it must never depend on being inside a window. |
| 5 | **Strict rooms.** A point outside every polygon is in no room, and a move with no room at either end passes. | The rule is inert wherever the tracing leaves a gap, and that is accepted. It will never refuse a legal move because a polygon was traced a few pixels short. |
| 6 | **Tokens are judged one at a time.** | No all-or-nothing group logic. Only the Keeper moves several tokens at once and the Keeper is exempt, so a player moves them one at a time. |

### Two facts this build rests on, both verified in the Foundry v14 client source

- **`preMoveToken` can refuse cleanly.** Returning `false` deletes the movement fields before any
  write and calls `#stopMovement`, so the token never leaves the room it is in. There is nothing to
  undo, and the teleport-back fallback is not needed.
- **Endpoints-only is not a compromise, it is the only thing that works everywhere.** On a gridded
  scene Foundry hands the hook every intermediate cell, so a path walk would be possible. On a
  gridless scene it hands over the endpoints and nothing else. ATLAS is built for hand-traced photo
  maps, which are usually gridless, so a path walk would silently behave differently from map to
  map.

### The trap this build must not fall into

A movement gate inside ATLAS would also apply to **a host system's own travel map**, which is an
ATLAS-shaped graph on a Foundry scene whose party marker moves by `token.update`. That fires
`preMoveToken`. Gating it would reverse two standing rulings about how travel works. So the gate
carries a `CONFIG` predicate that a host system widens, because ATLAS can only recognise its own
room labels and knows nothing about another system's markers, lamps or thrown weapons.

### Four ways to build the gate wrong

Each of these was found by reading the Foundry client source or the host system's own scars. Each
would produce a gate that looks finished and is not.

1. **The handler must not be `async`.** `Hooks.call` is synchronous and a Promise is truthy, so an
   async handler ALLOWS EVERY MOVE while appearing to work. The sibling call on the line above it in
   core IS awaited, which is what makes this look safe.
2. **Read `move.origin` and `move.destination`, never the token's current centre.** At this point in
   the pipeline both the document and the placeable still hold the ORIGIN, so a gate comparing centres
   compares A to A and never refuses anything. Convert each through the token's own centre-point
   helper, because a position is a top-left corner and a large token's corner is in the wrong room.
3. **Self-gate on the TOKEN's scene, and require the map to have connections, not just rooms.** The
   predicate correctly refuses every move on a map with no links, so a traced but unwired scene would
   freeze the moment the setting was turned on. A move can also be aimed at a scene nobody is viewing.
4. **The gate is a pure read.** It writes nothing, fires no hook, and forces no rebuild. It cannot
   know the move will happen even when it allows one, because later gates can still refuse it. A
   forced rebuild is how a host system once cleared every hidden creature's Hidden on a ward lamp drop.

## Part A: the movement restrictor

- [ ] **A0. The drag ghost stops moving people.**
  A standalone bug fix that must land BEFORE the gate, not after. Foundry builds a drag ghost that
  keeps the real token's id, and the boundary sensor has never ignored it, so during a drag the module
  remembers the room under the cursor instead of the room the token is in. When the token then really
  arrives there, the module sees no change and asks for no redraw. This is the "vision does not update
  until something else happens" you have hit before; the host system fixed the same bug in its own
  sensor in September and ATLAS never got the fix. A refusal is the case where the healing move never
  comes, so the gate would turn a tolerated flaw into a real one.
  *Test: as a player, drag your own token slowly from one room across into another and back, then
  drop. The fog is correct at every step with no extra click and no jiggling. Arrow keys will NOT
  exercise this: it has to be a drag, because only a drag makes a ghost.*

- [ ] **A1. The pure decision, with tests.**
  One transform, no Foundry anywhere near it: given the area data and two room labels, is this step
  legal? Tests pin your own example, the A-B-C-D line: A to B legal, A to C refused, A to D refused,
  D to C legal, same room legal, either end in no room legal, and B to A treated as the same edge as
  A to B.
  *Test: `npm test` is green. Nothing to see in Foundry yet.*

- [ ] **A2. The gate, behind a world setting, off by default.**
  The hook, the setting, and the `CONFIG` skip predicate. Off by default because this is a published
  module and an upgrade must not change how anyone's game already moves.
  *Test: trace four rooms in a line, connect A-B, B-C, C-D. Turn the setting on. As a player, drag
  A to B and it goes. Drag A to C and the token does not move, with a message naming both rooms.*

- [ ] **A3. Everything that must NOT be gated.**
  The Keeper, room labels themselves, undo, paste, and a scene with no areas traced.
  *Test: as Keeper drag a creature A to C and it goes, silently. Drag a room label and it moves.
  Lock, Redraw and Clear all still work. On a scene with no areas, everything moves freely.*

- [ ] **A4. The host system registers its skip.**
  The host side, in the system, not in the module: party marker, ward lamps, thrown weapons.
  *Test: on the travel map, a Keeper drag of the party marker to a league that is not adjacent still
  works and still spends nothing. Ward lamps and thrown weapons drop and drag normally.*

- [ ] **A5. A refused move leaves no trace.**
  A0 stops the ghost dirtying the record, but a refusal is still the one move that never completes,
  so the gate explicitly forgets the mover's remembered room on the way out. Forgetting is the safe
  repair rather than re-stamping, because a refused mid-path move can leave a token at a checkpoint
  that is neither where it started nor where it was going.
  *Test: as a player, drag A to C, get refused, then move A to B legally. The fog is right at every
  step, and nothing is revealed that should not be. Refuse twice in a row and nothing breaks.*

- [ ] **A6. The gap stops being a back door.**
  AGREED, AND DELIBERATELY LAST: this lands after Part B, on the user's word ("we can add it in once
  the current rebuild is done").

  Decision 5 says a token outside every traced room is unrestricted, which is right, but it can be
  used to launder a move: A to the gap is legal, the gap to C is legal, and the two together are the
  A to C the rule exists to refuse. The fix is to remember the last room a token was really INSIDE,
  and to judge a move that starts nowhere from there instead.

  The memo is written from the boundary sensor, after a move has actually landed, and only when the
  strict lookup returns a real room, so standing in a gap leaves it holding the last real room. It is
  never written by the gate, which stays a pure read, and it costs nothing while the setting is off.
  With no memo yet, on a fresh reload, it falls back to allowing, which is today's behaviour.
  *Test: with the setting on, drag A into the gap between rooms (allowed), then from the gap into C.
  The second move is refused and names A and C. Reload, stand a token in a gap with no history, and
  confirm its first move is allowed rather than refused on a guess.*

## Part B: the node control window

### What the panel will NOT inherit, and must supply for itself

Found by reading `styles/atlas.css` against the card's markup. Each one is silent: the panel will
render, and look subtly wrong, with nothing in any test going red.

- **Window padding.** `.atlas-marker-sheet .window-content { padding: 0 }` is the ONLY card rule
  scoped to the sheet's class, and the panel will not have that class. Without its own copy the
  panel gets Foundry's 16px on top of the card's own 20px by 22px, so the card reads as inset and
  the effect chips lose about 32px of width between them.
- **Overflow.** Foundry's `.window-content` is `overflow: hidden`. The editor window needed its own
  `overflow: auto` for exactly this, and a resizable panel without it CLIPS rather than scrolls,
  which only shows once the panel is shorter than its contents.
- **The gap under the room name.** In write-through mode the hint paragraph is gone, and its
  `margin: 0 0 12px` was the only thing separating the room title from the sight toggles. Without a
  rule of its own the panel's toggles sit 2px under the title, tight against 20px of top padding.
- **The copy is still the sheet's.** The None chip's tooltip says "Stage ALL effects off", which is
  wrong on a surface where the click has already landed. B2 rewrites the strings it keeps.
- **B4's rename field is scoped to `.atlas-ed`**, which only the editor emits, so a rename input in
  the panel arrives with the wrong height, the wrong font and no focus ring.
- **There are no design tokens.** The stylesheet has zero custom properties; the palette is repeated
  literally in every rule. The panel inherits the card's look ONLY by emitting the card's exact
  class names, so any chrome it adds beyond the card copies hex values by hand. The drift the B1
  lift prevented on the JavaScript side is still wide open on the CSS side.

- [ ] **B1. One builder, two surfaces.**
  Lift the card body out of the marker sheet into a pure function, and have the existing sheet call
  it. No behaviour change at all in this checkpoint. Tests pin the produced HTML.
  *Test: double-click a room label. The card looks and behaves exactly as it does today, including
  the amber staged state and Apply being disabled until something changes.*

- [ ] **B2. The window, and the macro that opens it.**
  A single window, `ATLAS.openRoomPanel()`, so your macro is one line.
  *Test: run the macro. A window opens showing one room's controls, and toggling line of sight in it
  changes the map.*

- [ ] **B3. Left-click a node and the window follows.**
  The retarget, pinned per token instance rather than on the prototype, which is how the module
  already keeps host right-click menus off room labels.
  *Test: with the window open, left-click room A then room B then room C. One window throughout, and
  it always shows the room you last clicked. Token selection and dragging still work normally.*

- [ ] **B4. Rename in the panel.**
  *Test: rename a room in the panel. The map label changes and the editor's matrix agrees. Clear the
  name and it falls back to a letter.*

- [ ] **B5. The card is retired, and a click anywhere in a room is enough.**
  DECIDED 2026-09-23, on the user's word: "the double click should open the new window a single
  clikc should swap areas, any click in the area not just the lable should swap areas. we can retire
  the oldmethod". With it: the letter-and-name readout and the name field under it were saying the
  same thing twice, so they became one row, the letter beside the field.

  The canvas picker is PASSIVE: it reads a click and never consumes one, so selection, dragging,
  panning and the drawing tools are untouched. It ignores any gesture that moved more than 8px, or a
  pan across the map would retarget on release, and it keeps out of the way while a room is traced.
  *Test: double-click a room, the panel opens on it. Click inside another room anywhere, not on its
  label, and the panel follows. Drag the map across three rooms and release: the panel does not move.
  Double-clicking a label no longer opens the old card.*

## Part C: blackout, and doorways

Two features asked for 2026-09-23.

**BLACKOUT** hides a room from the table entirely, so a secret can sit on the live map. **A DOORWAY**
is a sight block on one connection: sight cannot cross it in either direction, and nothing else about
that connection changes.

### The decisions that govern them

| | Decision | What it rules out |
|---|---|---|
| 7 | **A blackout SEALS sight.** Nothing in it is seen, it sees nothing out, and sight does not cross it. | Not just hiding the outline. A creature left visible in a room that is supposedly not there would be worse than no blackout at all. |
| 8 | **A blackout refuses movement whatever else is true**, including when the connection rule is switched off. | It is not part of the connection restriction. A table that never turns that on still gets closed secret rooms. |
| 9 | **A doorway blocks SIGHT ONLY.** | It never disconnects the rooms, never blocks movement, never changes hop distance, and a token walking through never opens it. |
| 10 | **A doorway on two rooms with no connection is refused**, with a message, and the tool stays armed. | No silently creating a travel route as a side effect of placing a door. |
| 11 | **The door icon is drawn for everyone**, at the midpoint of the connection. | Players see where sight is stopped. Reversible later if it gives too much away. |

Two things the user chose and may want to revisit once they are in play:

- **The connection LINES into a blacked-out room still show.** Four lines converging on an empty patch
  of map say "something is here" nearly as loudly as the outline did. One line to change.
- **A doorway does not stop a host system's SENSE effect** (a tremor sense reaching through the ground
  walks its own graph deliberately). That reads correct, but it is a real difference from sight.

### Shapes, decided while building

- Doorways live in their **own array** beside `connections`, never as a third element on each pair, so
  every scene traced before doorways existed needs no migration.
- **Present means blocked.** There is no stored "open doorway", because an open door and no door are
  the same thing to sight. Removing the entry is how you turn one off.
- A doorway is implemented as **an edge the SIGHT graph does not have**, so the travel graph is
  untouched by construction rather than by care.
- Blackout **never writes** `losIn`/`losOut`/`losThrough`, so lifting one restores the room to exactly
  what the Keeper had set, not to a default.

- [x] **C1. The rules, pure and tested.**
  Doorways, the sight graph, blackout sealing, and the movement refusal. 22 tests, including the ones
  that pin the two things easiest to get wrong: that a doorway changes sight and NOT distance, and
  that a blackout seals a room whose own three switches are all explicitly open.
  *Test: `npm test` is green. Nothing to see in Foundry yet.*

- [x] **C2. Blackout on the canvas.**
  For the Keeper: the room goes black and hatched, label still readable, exactly as drawn in the
  mockup. For a player: no outline, no label, nothing inside it, and no sight across it.
  *Test: black out a room with a creature standing in it. As a player: the room is not there and
  neither is the creature, and a room beyond it is no longer visible. As Keeper: hatched, labelled,
  everything still selectable.*

- [x] **C3. The blackout toggle on the panel.**
  BUILT WITH C2: a canvas treatment with no way to switch it on is not a checkpoint anyone can test.
  An icon on the room panel, reflecting the room's current state.
  *Test: toggle it on and off with a player watching. The room appears and disappears for them at
  once, with no reload and nothing to click on their side.*

- [x] **C4. The door icon on the line.**
  A small door drawn at the midpoint of a blocked connection, visible to everyone.
  *Test: place a doorway, see it on the line. Remove it, the icon goes. Retrace one of the two rooms
  and the icon follows the line to its new midpoint.*

- [x] **C5. The doorway gesture on the panel.**
  BUILT WITH C4, for the same reason C3 went with C2: an icon you cannot place is not testable.
  The interception lives in ONE place, `retargetPanel`, so every route that would otherwise move the
  panel (a label click, a click anywhere inside a room) completes the doorway instead. The gesture
  toggles, so arming on A and clicking B a second time takes the doorway away again.
  A doorway icon arms the tool with the panel's room as one side; the next room clicked is the other.
  The panel shows it is armed. Escape, or clicking the armed room again, cancels. A new doorway is
  blocking immediately.
  *Test: arm on A, click B: sight between them stops, movement does not. Arm on A, click a room A is
  not connected to: refused with a message, and the tool is still armed. Arm and press Escape:
  nothing happens and nothing is left armed.*

## Not in this build, but waiting

These are known and deliberately not scheduled. They are here so they are not rediscovered as
surprises.

- **The hex draw tool.** Spec'd 2026-09-05 and never built: draw one hex, and every later press
  stamps a copy of it. The seams are already scouted.
- **Orphaned rooms.** Delete a room's label token with the Delete key and its record, polygon and
  connections survive. The sweep that would fix this is written and tested but called from nowhere.
  The movement gate makes this worse, because it would enforce a room nobody can see or select.
- **Release chores.** `package.json` says 0.4.0 against `module.json`'s 0.5.0, the download URL
  still names the v0.4.0 zip, and the README claims v0.4.0 and 51 tests when 80 pass. These belong
  with a release being cut, not with a feature.
